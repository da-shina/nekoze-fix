# Main受け渡しゲートの結線判断（フェーズ鏡像・計測・排出）

## 概要

`mainactor-throttle` の呼出結線（tasks 3.1）にあたり、design.md の結合擬似コードと現行コードの制約が衝突した3点（フェーズ読取り・能動排出・計測値の寿命）と、数値既定（表示更新間隔・比率許容誤差）の根拠をここに確定する。判定則・3秒確定・通知・UI の振る舞いは変えない。

## 詳細

- フェーズ鏡像：design.md は `snapshot.phase` の「検出キューからの既存の読取り経路」に従うと記すが、そのような経路は存在しない（`snapshot` は `@MainActor` 隔離、`captureOutput` は nonisolated の同期実行であり、hop なしの同期的読取りは actor 境界上不可能）。このため `LockedMainHopGate` 内に軽量フェーズの鏡像を持ち、唯一の書込み経路 `setPhase` から反映する。検出キューは snapshot に触れず鏡像のみ読む。初期値は fail-open の `.calibrating`（初回反映前の判定機会を保つ）。写像は `calibrating→.calibrating、それ以外→.monitoring`（design 対応表通り）
- 数値既定：表示更新間隔の既定 0.1秒は research の「0.5秒系グレースより十分小さい」を満たす最大級の粗さ（10Hz 配送で Main 投入を約1/6に削減しつつ通知予算 0.5秒に5回分の余裕を残す）。比率許容誤差 1e-3 は同一解像度の同一ビット値（整数除算）と実変化（4:3→16:9 で約0.44）の間に十分な分離がある。いずれも注入時に定まり判定中に変わらない（design Invariants 準拠）
- 排出：能動排出トリガは結線しない。定常時は 0.1秒ごとに次回 deliver が発生し表示の古びは間隔内に収まる。フレーム到達自体が止まる経路（背景・停止・カメラ切替）は既存の初期化配送でスロットを破棄する。明示停止を伴わない到達停止（セッション中断等）では排出前と同一の凍結表示になるが、これは削減前の毎フレーム Task 生成時と同一の振る舞いであり回帰ではない
- 計測値の寿命：`reset()` は判定状態・スロット・計数をともに初期化する（design State model 通り）。長期記録（Req 7.1）は停止・再開をまたぐ系列が必要なため、5秒定期ログに受け渡し計数（申請・配送・集約破棄・排出待ち）を同梱し、ログ系列で追えるようにする。リセット前の個別読出しは行わない
- 待ち時間の定義：排出待ちは初回集約→排出の間隔（最長待ち）とする。Req 1.1「Mainでの反映を待つ待ち時間」は集約された検出結果群の待ちであり、最終集約起点では過小評価になる。無効時刻の配送はスロット排出済みとみなし起点を残さない
- 計測読出し面（`snapshot()`・`pendingCount`・写像関数）は design Service Interface の最小形を超えるが、Req 1.3「計測値を検証時に読み出せること」と Req 7.1 の記録に必須のため正当な範囲とする。`submit` の4引数署名は design 準拠のまま（`Submission` 型への束ねは見送り）

## 検討した選択肢

- snapshot の Main hop 読取り（検出キュー→Main へ都度 hop してフェーズを読む）：毎フレーム hop が復活し削減目的と矛盾する（却下、鏡像を採用）
- 能動排出タイマ：新規スレッド機構であり design Non-Goals「新規スレッド機構の導入」に抵触する（却下）
- リセット時の計数温存（`resetCounts` 分離）：ゲート Interface を design 超過で広げる。定期ログ系列で代替できるため見送る（却下）
- コメント用語の `校正`→`キャリブレーション` 置換：CONTEXT.md と既存 Session 層が `校正／校正中` を多用しており、単独置換は不整合を生む（却下、現行維持）
